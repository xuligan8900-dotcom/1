Падение остаётся физическим, после смерти используется прежний чекпоинт.

В магазине добавлена вкладка «Дубинки», покупка за монеты и сохранение выбранного типа. Старые балансы/косметика сохраняются; деревянная выдаётся старым аккаунтам бесплатно. **Две донатные дубинки отключены до создания Game Pass и заполнения двух PassId** в CommerceConfig. ## Исправление запуска v3.1

Откройте **`build/MechanicalTower-v3.1.rbxlx`** из свежего GitHub-архива (или `MechanicalTower-v3.1.rbxlx` из вложенного пакета). Это отдельное имя, чтобы не перепутать с уже открытым старым place.

В v3 StudioSmoke сравнивал размер `Part.Size.X` с литералом2,8/6,2 на точное равенство. Движок хранит размер в float32: например6,2 превращается в6,199999809. Проверка ложно падала до подключения обработки входа игроков, а CharacterAutoLoads уже был выключен: карта могла создаться, но персонаж не появлялся.

В v3.1 сравнение использует допуск0,001stud; тест float32-round-trip воспроизводит и проверяет эту регрессию. StudioSmoke по-прежнему выполняется и сообщает PASS/FAILED, но запускается после подключения игрового цикла; его результат отражается в Workspace.TowerDiagnosticsPassed. Ошибки генерации и обязательных инвариантов не скрываются. Теперь отдельный экран показывает стадии загрузки или сообщение об ошибке, даже если Shared/Remotes/карта ещё не готовы.

## Изменения v3: промежутки и ловушки после CP14

- Радиус маршрута увеличен до 42 studs; обычные платформы укорочены. Реальный зазор между краями соседних неподвижных площадок — минимум **1,899 studs** с учётом их поворота. Между центрами — максимум 6,092 studs. Для движущихся площадок промежуток меняется при стыковке.
- На этапе **15, сразу после чекпоинта 14**, короткие трёхлопастные механизмы заменили огромные перекрёстные балки. Лопасти больше не достают до центра площадки ожидания. Зелёное окно — минимум **5,5 секунды**, скорость этого этапа снижена.
- У всех наносящих урон механизмов зелёная фаза теперь действительно безопасна. Жёлтая — предупреждение, красная — опасность. Вращение визуально продолжается и в зелёной фазе, но урона нет. Физические прессы и двери в безопасной фазе открыты с запасом по высоте R15.
- Для остальных станций зелёное окно не короче 3,6 секунды, предупреждение — не короче 1,2 секунды. Это оставляет время на вход и выход через увеличенные разрывы.
- Двойные балки находятся в одной низкой плоскости; убрана верхняя перекладина, ограничивавшая прыжок. Молоты и зубья шестерёнок компактнее, лишний верхний лазер удалён, дверь закрывается плавно после предупреждения.

## Быстрый запуск в Roblox Studio

1. Распакуйте весь архив. В Roblox Studio выберите **File → Open from File** и откройте `MechanicalTower.rbxlx` из архива (в репозитории — `build/MechanicalTower.rbxlx`). Не импортируйте его как модель в другой place.
2. Выберите R15 в настройках аватара проекта: **Game Settings / Avatar** (в новых версиях Studio — Avatar Settings). Скорость 16, JumpPower 50 и гравитация 196.2 выставляются проектом и сервером. Дополнительные прыжки или спринт не нужны.
3. Откройте **View → Output**, нажмите **Play / F5**. Карта создаётся автоматически на сервере. В Edit до Play башня не отображается: это предусмотренный runtime-генератор.
4. Ожидаемые сообщения: `[Tower] READY: 50 stages, 50 checkpoints…`, `[StudioSmoke] PASS…`, затем `Server initialized`. Персонажи появляются только после готовности карты и загрузки данных.
5. Следуйте неоновым полосам и стрелкам. Зелёный/жёлтый/красный сигнал обозначает состояние ловушки; зелёные вращающиеся детали безопасны, красные опасны. На каждом этапе есть безопасные остановки на узлах 4 и 8.
6. Падение не телепортирует на чекпоинт: открытое страховочное перекрытие останавливает падение внутри башни, от него можно подниматься снова. Смерть от красной ловушки или нижней KillZone возвращает на последний чекпоинт текущего забега. Через меню Roblox можно использовать Reset Character.

**Проверено в облаке:** компиляция Luau, 9550 автоматических проверок чистых модулей, сборка Rojo и структура XML. **Roblox Studio здесь не запускался.** Приложен готовый place и автоматическая Studio-диагностика; физику, игровой баланс, сетевую задержку, DataStore и мобильный HUD необходимо проверить по [docs/TESTING.md](docs/TESTING.md) перед публикацией. Это реализованный проект для дальнейшего Studio playtest, а не заявление о завершённой сертификации всех 50 этажей.

## Редактирование исходников через Rojo

Готовый place позволяет обойтись без установки Rojo. Для дальнейшей разработки используйте Rojo **7.7.1** и официальный плагин Rojo в Studio.

```sh
rojo build default.project.json -o build/MechanicalTower.rbxlx
rojo serve default.project.json
```

Каталог `build` нужно создать перед первой сборкой. В новом пустом place подключите плагин к серверу Rojo. Не подключайте одновременно несколько проектов, содержащих `TowerServer`, к одному place. Rojo синхронизирует исходники; карту создаёт сервер при Play. Остановите Play перед изменением конфигурации маршрута.

Для этой Linux x86_64 облачной среды:

```sh
cd /workspace/1
python3 tools/bootstrap.py
python3 tools/verify.py
```

Скрипт загружает официальные закреплённые релизы по HTTPS и проверяет SHA-256 из `tools/versions.json`. Повторный запуск использует проверенный кеш. Глобальные пакеты не нужны. Для Windows/macOS установите официальный CLI Rojo отдельно либо откройте готовый `.rbxlx`; Linux-бинарники из bootstrap там не работают.

## Сохранение DataStore

По умолчанию **в Studio данные только в памяти сессии**. HUD явно показывает `STUDIO · Session only`. В опубликованной игре DataStore включён автоматически; токены или секреты в коде не нужны.

Для проверки реального сохранения:

1. Опубликуйте **отдельный тестовый place/experience** через **File → Publish to Roblox**.
2. В **Game Settings → Security** включите **Enable Studio Access to API Services**. Для production-place не включайте Studio-доступ без необходимости: Studio использует настоящее хранилище этого experience.
3. В `src/shared/GameConfig.luau` выставьте `StudioPersistence = true`, пересоберите/синхронизируйте проект. При работе непосредственно с place измените соответствующий ModuleScript в `ReplicatedStorage/Shared`.
4. Пройдите чекпоинт, дождитесь `Progress saved`, завершите тест, войдите снова. Персонаж должен появиться на последнем сохранённом чекпоинте.
5. Для разработки можно сменить `DataStoreName` на отдельное тестовое имя. Это создаёт другое пространство ключей, а не переносит или удаляет существующие данные.

`UpdateAsync` сохраняет максимум этапа и минимум времени полного забега. Новые этапы объединяются в запись с задержкой 8 секунд, автосохранение — каждые 30 секунд; выход и завершение сервера также сохраняют данные с ограниченными повторными попытками. Как у любого DataStore-проекта, аварийное отключение сервера до успешной записи может потерять последние несохранённые секунды прогресса. Ошибка загрузки не заменяет существующий профиль нулевым: игрок получает сообщение с просьбой перезайти. Ошибка записи сохраняет признак pending и повторяется при следующем сохранении.

## Прогресс и повторный забег

- `RunStage`: чекпоинт текущего забега, используется для возрождения.
- `MaxStage`: максимальный сохранённый результат, никогда не уменьшается.
- `Completed`: постоянная победная отметка.
- `BestTime`: лучшее время **полного** забега от старта до 50-го этапа.
- При повторном входе текущий забег начинается с сохранённого максимума. Таймер показывает время этой сессии; неполный забег не может обновить рекорд полного прохождения.
- После победы кнопка **Play Again** начинает забег с основания, сохраняя максимум и отметку победы. Если выйти во время повтора, следующий вход снова использует сохранённый максимум, а не промежуточный прогресс повтора.
- Количество смертей и таймер относятся к текущей сессии. Play Again обнуляет таймер, но не счётчик смертей.

Клиенту доступен только запрос Play Again; сервер принимает его лишь после победы и с ограничением частоты. Чекпоинты выдаются серверной проверкой контакта с площадкой и порядка этапов. Скрытые промежуточные области оставлены только для диагностики и не влияют на выдачу прогресса. Это защищает от поддельных progress-remotes; полноценная защита от изменённого клиента, летающего между серверными точками, требует отдельного античита.

Все GUI и RemoteEvent создаются программно. Перезапуск генератора в той же сессии возвращает готовую башню; незавершённая генерация вызывает явную ошибку вместо дубликатов.
